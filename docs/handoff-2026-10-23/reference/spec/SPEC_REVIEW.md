## 3. 已解決矛盾

| 問題 | 現行規則 | 文件對應 |
|---|---|---|
| 原圖不得刪 vs 刪專案釋放空間 | 專案使用中保護；明確刪整專案可清原始備份 | FR-019/030；架構§7；TC-D01 |
| 待恢復不得清備份 vs 使用者可放棄 | 正常恢復保留；明確放棄並刪專案為例外，不寫遊戲 | FR-022/030；架構§6/7；TC-D03 |
| 已部署版本不可刪 vs 可刪專案 | 一般歷史不可刪；整專案可保留遊戲現況並刪 | FR-009/030；TC-D02 |
| 靜態PNG vs 早期多格式/動畫 | PoC/MVP只靜態PNG，其他格式/動畫Future | DEC-009；FR-008/029；TC-P09 |
| 取消目前替換 vs 還原 | 前者只清active，後者明確寫原始位元組 | FR-011/019/020；TC-020 |
| 回復原圖 vs 失敗恢復 | 還原是original；recovery是操作前，可能V1 | FR-019/022；TC-P06 |
| 原型允許外部衝突覆蓋 | 套用與還原一律阻擋外部變更 | FR-021；TC-021 |
| 視窗與工具列版本不一致 | 應用內獨立頁；工作臺W6排列 | FR-027/028；設計索引 |

刪除尚在活動寫入中的檔案會產生競態。規格要求先安全停止活動工作再清理，不要求使用者先完成恢復；與允許放棄恢復的決策一致。

## 5. 尚未驗證的技術風險

1. MV/MZ不同部署與加密路徑能否正確識別及寫回，必須遊戲內驗證。
2. 檔案與metadata沒有共同交易，崩潰窗口、磁碟滿及恢復失敗須故障注入。
3. 原始位元組保存及已部署hash管理不得混用解碼後PNG。
4. 專案清理的引用、路徑連結、共用DB與實際磁碟回收須驗證。
5. APNG識別、透明通道與超大PNG解碼行為須實測。
6. 遊戲位置別名/搬移判定、原生依賴Windows打包與最低版本未定。

相關測試已規劃，但沒有任何應用測試結果可報PASS。
