# Proposed Architecture — RPG Maker 圖片替換工具

版本：1.0.0｜日期：2026-10-22｜產品基準：[PRD 1.0.0](PRD.md)，R0.9。

狀態：**Proposed Architecture**。Electron、React、Vite、TypeScript 已由使用者選定；以下模組、儲存、函式庫及恢復演算法為規劃，尚未實作驗證，不代表完成。

## 1. 架構目標與界線

2026-10-23 核心開發補充：掃描採主程序持有的一次性確認 token 與來源 hash 快照，確認時再次核對，僅新增未登記路徑；既有基準保持不可變。新增窄 IPC 提供位置狀態、掃描差異及提交。拖放由 preload 取得 File 對應來源，main 僅作圖片驗證與短期匯入 token，不向 renderer 提供通用檔案讀寫。active=null 與 deployed 不同也列入待套用，沿用操作日誌、原始 bytes 與操作前恢復協議。

Windows離線桌面使用；MV/MZ標準圖片檔案；原圖不可變、輸入與遊戲寫入分離、版本可追蹤、失敗可識別。只修改指定圖片，不改遊戲事件、程式、外掛。動態播放、格式轉換、其他平台/引擎屬Future。

產品行為以PRD為準。本文件可在PoC證據支持下調整技術，但不能以實作方便為由移除恢復、放寬格式或改變刪除政策。

## 2. 候選技術與選擇理由

| 項目 | 狀態 | 理由/代價 | 驗證 |
|---|---|---|---|
| Electron | 已選路線，未驗證 | 桌面檔案/視窗整合；需控制程序權限、打包與資源消耗 | 打包後讀寫、權限錯誤、重啟恢復 |
| React | 已選路線 | 對照列表、彈窗、狀態呈現；不應承擔遊戲檔案直接操作 | 狀態交互與大量清單 |
| TypeScript | 已選路線 | 模組/IPC契約可檢查；型別不取代執行時驗證 | 外部輸入及錯誤回傳驗證 |
| Vite | 已選路線 | renderer開發/建置；不等於Electron封裝工具 | 開發/打包載入路徑 |
| SQLite | 候選 | 單機metadata/交易；需遷移及Windows打包驗證 | 崩潰一致性、原生依賴、實際空間回收 |
| JSON檔metadata | 備選而非同時採用 | 小型PoC容易檢查；多物件交易與可靠更新需另做 | 不足時不得省略恢復要求 |
| 檔案系統圖片庫 | 候選 | 圖片/備份可逐檔驗證，避免大blob耦合DB | 孤兒檔、權限、磁碟滿、清理 |
| Sharp等圖片函式庫 | 候選 | 縮圖/解碼能力需實測，不能預設能正確拒絕APNG | PNG內容判斷、動畫標記、透明/色彩與記憶體 |
| 虛擬列表/縮圖快取 | 候選 | 控制大量圖記憶體 | 效能數據後選型；不是新增產品功能 |

版本鎖定、封裝工具、SQLite binding與測試框架留待開發規劃，未安裝任何套件。Tauri等先前討論不再是本次已選路線，不自行重開選型。

## 3. 程序邊界與模組

建議renderer僅渲染本機UI，透過窄化preload API呼叫main服務；啟用隔離、避免將通用IPC或任意檔案操作暴露給renderer。每一命令驗證來源、輸入與專案/素材ID。繁重解碼/掃描考慮worker或utility process，具體選擇待測。不得載入遊戲JavaScript來做不受控識別。

| 模組ID | 職責 | FR對應 |
|---|---|---|
| UI | 頁面、彈窗、焦點、選取、預覽操作、進度與鎖定 | FR-005, FR-006, FR-010, FR-012, FR-016, FR-024, FR-025, FR-027, FR-028 |
| PROJECT | 專案生命週期、位置識別、隔離、重新連結 | FR-001, FR-002, FR-023, FR-030 |
| ENGINE | MV/MZ adapter、掃描、格式/加密辨識、相對路徑與遊戲檔案讀寫邊界 | FR-002, FR-015, FR-021, FR-023, FR-026, FR-029 |
| CATALOG | 素材索引、資料夾、多群組、搜尋/篩選 | FR-003, FR-004, FR-012, FR-025, FR-026 |
| IMAGE | 靜態PNG檢查、差異資訊、縮圖、預覽資料 | FR-008, FR-010, FR-025 |
| VERSION | 原圖/active/deployed語意、版本號、歷史刪除保護 | FR-007, FR-009, FR-011, FR-020 |
| IMPORT | 單張/批次暫存、配對、差異接受、整批提交/撤回 | FR-007, FR-008, FR-013 |
| EXPORT | 範圍、來源版本、PNG輸出、衝突預檢、實際結果 | FR-014, FR-015 |
| STORE | metadata、不可變檔案、儲存狀態、日誌、重啟恢復資料 | FR-017, FR-019, FR-020, FR-024, FR-030 |
| OPERATION | 套用/還原協調、備份、外部衝突、鎖定、失敗恢復 | FR-018, FR-019, FR-021, FR-022 |
| DELETE | 專屬資料清理、放棄恢復確認、範圍保護、重試 | FR-030 |

IPC候選命令：scanProject、importVersions、exportAssets、selectVersion、applyPending、restoreSelected、recoverOperation、deleteProject。這是契約名稱提案，不是現有API。使用asset/project ID由main解析路徑；不可相信renderer傳入的任意刪除路徑。

## 4. 資料模型與圖片管理（提案）

| 實體 | 必要資料/不變條件 |
|---|---|
| Project | id、名稱、引擎、遊戲位置、正規化位置身分、建立時間、保存/恢復/刪除狀態 |
| Asset | projectId、原始相對路徑、遊戲格式、原始blobId/hash、尺寸/比例/透明通道、基準就緒狀態 |
| Version | assetId、單調遞增序號、原始上傳檔、PNG檢查結果、差異接受紀錄、時間；不重用序號 |
| Selection | assetId→activeVersionId或空；不與預覽暫態混用 |
| Deployment | assetId→最後可信版本/原圖、實際遊戲hash、操作id；中斷/衝突另標示 |
| Group/GroupMember | projectId、groupId、assetId多對多；刪關聯不刪素材 |
| Operation/OperationItem | 類型、狀態、目標清單、操作前hash/備份、預期寫後hash、逐檔進度、錯誤 |
| DeletionJob | 專案身分、限定清理清單、使用者確認結果、未完成清理項；清完後移除專案內容 |

建議每專案有獨立工具管理目錄，圖片、基準與備份放其內；metadata可以共用DB或每專案DB，待PoC規劃選定。若共用檔案，必須引用計數且不得刪除其他專案仍引用的內容；首版可避免跨專案去重降低風險。

原始加密檔案需保存原始位元組，不以解密後重編碼的PNG代替還原備份。預覽/匯出用可解碼PNG衍生物；匯入靜態PNG原檔保存，非PNG拒絕，不執行轉檔。縮圖僅衍生快取，不當還原來源。

雜湊候選SHA-256；檔名/修改時間不能單獨作完整性證明。資料庫transaction不涵蓋遊戲檔案系統；二者需協調日誌與恢復，不宣稱多檔案天然原子。

## 5. 讀取、匯入與匯出

### 建立與掃描

確認乾淨來源→識別引擎/資產根→列相對路徑→讀取並保存原始位元組→hash驗證→解密/解碼檢查→metadata與縮圖。來源可能在掃描中變更，需比較讀取前後或穩定快照策略；不穩定來源不得標示基準完整。取消與壞檔保留準確結果，未完成基準項禁止套用。

### 匯入

暫存輸入→內容格式/動畫/解碼檢查→與原圖比較→唯一相對路徑配對或人工指定→接受差異→準備整批檔案→metadata提交。保存失敗整批不生效；檔案系統殘留需可重試清理，不把暫存當正式版本。事務邊界與崩潰後清理策略由PoC驗證。

### 匯出

確定範圍→解析original或active（缺少回退原圖）→轉出可編輯PNG（加密素材解密，而非非PNG轉檔）→預檢同名衝突→覆蓋/略過/取消→寫出並回報逐檔結果。寫入前再次檢查目的地避免預檢後競態。使用者明確授權覆蓋僅限清單目標，不允許路徑穿越。

## 6. 遊戲寫入、還原與中斷恢復

候選步驟適用套用與還原；還原的輸出為原始位元組：

1. 取得專案/遊戲位置操作鎖，禁止同時套用、還原、重新連結、清理。
2. 建立不可變操作清單，檢查儲存成功、基準可用、格式有效與必要接受紀錄。
3. 比對每個目標實際hash與最後可信部署hash；有外部變更/遺失則整批在寫入前阻擋。
4. 保存每檔操作前位元組及hash；建立可持久化操作日誌。尚未證明備份成功不得動遊戲。
5. 準備目標輸出與預期hash，檢查磁碟/權限。這類預檢不能保證稍後不失敗。
6. 按adapter寫入目標（必要時加密）；可採同檔案系統暫存替換，但不假設整批原子；每一步更新可恢復進度並驗證。
7. 全部檔案寫後hash驗證成功，再提交部署metadata與operation成功狀態。
8. 任一步失敗：嘗試回到操作前狀態，驗證每檔。若恢復也失敗，保留日誌與備份，標示recoverable/failed而非success。

寫完檔案但DB未提交、日誌已寫但檔案未寫等窗口都須覆蓋。恢復應具可重入性，重跑不重複破壞資料。若恢復時又發現第三方修改，不得盲目覆蓋；可識別的預期前/後hash以外應停止並回報需處理的衝突。

重啟不自動靜默寫遊戲：先顯示未完成操作，使用者選開始恢復；其他正常專案不因此全面鎖定。恢復失敗仍可重試/關閉，使用者另可明確放棄並刪除專案（第7節）。

成功顯示由檔案驗證與持久化狀態共同決定；程式內驗證不代替TEST_PLAN要求的人工遊戲內場景確認。

## 7. 刪除專案與強制放棄（FR-030）

現行決策允許保留已部署遊戲結果刪專案，也允許放棄未完成恢復。不能沿用舊提案要求先還原才可刪除。

候選流程：顯示專案/清理範圍→第一次不可逆警告→依部署/中斷狀態追加確認→取得清理鎖且確保沒有活動寫入worker→記錄刪除工作→清理專屬檔案與DB→驗證範圍與結果。若有活動寫入，先等作業安全停止，不在寫入中抽走備份；這不等於強迫使用者完成恢復。

刪除只允許工具管理根下已確認屬該專案的檔案；防止符號連結/目錄接合導向遊戲或其他位置。不刪整個共用DB、不刪其他專案、不刪外部原圖或匯出。失敗保留最小清理紀錄供重試，不假稱已釋放全部空間；成功後刪除專案內容。SQLite DELETE可能不立即縮小檔案，實際空間回收方法待驗證，不向使用者保證未量測的數字。

## 8. MV/MZ相容性驗證

兩個adapter可共用介面：detect、listAssets、decodeForPreview、encodeForTarget、verifyTarget；不可先假設兩引擎加密完全相同。需測資產根位置、加密副檔名/標頭/金鑰取得方式與不同部署配置。常見MV加密圖片`.rpgmvp`、MZ`.png_`僅作候選辨識線索；實際相容性以合法樣本及遊戲內結果為準，不單看副檔名。

官方MV/MZ素材規格說明圖片採PNG；不代表所有PNG動畫/特殊變體都支援。本產品額外限定可解碼靜態PNG，拒絕APNG。自訂加密/特殊封裝回報不支援，不試圖靜默套用。

## 9. 風險與驗證對應

| 風險 | 影響 | 驗證 |
|---|---|---|
| 多檔案/DB無共同交易 | 半套用、錯誤部署狀態 | TC-P04、TC-P05、TC-P06 |
| 加解密或路徑推斷錯誤 | 遊戲無法載入/寫錯檔 | TC-P01、TC-P02、TC-P03、TC-029 |
| 備份不完整/磁碟滿/檔案占用 | 無法回復 | TC-P04、TC-P07 |
| 外部修改/程序並行 | 覆蓋未知內容 | TC-021、TC-P08 |
| 放棄恢復後刪除 | 永久失去工具恢復能力 | TC-030、TC-D01～TC-D05，產品已接受但需明確確認 |
| 路徑別名/連結/清理邊界 | 誤刪其他資料 | TC-023、TC-D04 |
| 圖片解碼資源/PNG動畫判斷 | 當機或非支援圖被接受 | TC-008、TC-P09 |
| 版本/部署混淆 | 刪錯或還原錯誤 | TC-009、TC-020 |
